## 1. 设计目标与原则

### 1.1 设计目标

- **零成本运行**：首版纯本地，无服务器、无 API 费用。
- **离线可用**：无网络时搜索、浏览、话术全部可用。
- **极致轻量**：主包 < 1MB，冷启动 < 2s，搜索 < 500ms。
- **可演进**：架构预留 V2.0（云开发 + AI）、V3.0（独立后端）平滑升级路径。

### 1.2 设计原则（Design Principles）

1. **KISS**：当前阶段用最简单可落地的方案，不引入不必要复杂度。
2. **渐进式架构**：本地架构 → 云开发 → 独立后端，每步平滑升级不推倒重来。
3. **依赖倒置**：上层依赖接口，不依赖实现，便于后端迁移零改动。
4. **配置化运营**：搜索权重、热门词、功能开关配置化，动态调整免发版。
5. **数据代码分离**：内容与代码解耦，运营可独立维护数据。

### 1.3 质量属性优先级（ATAM 视角）

| 质量属性 | 优先级 | 说明 |
|----------|--------|------|
| 性能（冷启动/搜索） | 高 | 用户体验直接感知 |
| 可维护性 / 可演进性 | 高 | 预留 V2.0/V3.0 接口 |
| 离线可用性 | 高 | 无网络核心功能可用 |
| 安全合规 | 最高 | 不可妥协红线 |
| 可观测性 | 中 | 当前本地日志，V2.0 上报 |

## 2. 技术选型与决策（ADR）

> ADR（Architecture Decision Record）：记录关键选型、候选对比、决策与后果。遵循「状态：采纳 / 弃用 / 备选」标注。

### ADR-1 前端框架：微信小程序原生

| 候选 | 优势 | 劣势 | 状态 |
|------|------|------|------|
| 微信小程序原生 | 性能最优、包体积最小、开发最快 | 仅微信平台 | ✅ 采纳 |
| Taro (React) | 跨端、组件化 | 包体积大（+300KB）、性能损耗、依赖多 | ⚠️ V3.0 备选（多端发布评估） |
| uni-app | 跨端 | 性能损耗、调试复杂 | ⚠️ V3.0 备选 |
| 微信小程序 + TypeScript | 类型安全 | 增加编译步骤 | ⚠️ 可选，V2.0 可迁移 TS |

**决策**：当前仅微信平台、数据量小、功能简单，原生开发性能与体积最优；多端发布（H5/PC/APP）纳入 V3.0 规划，届时按 Taro / uni-app 评估跨端方案，不阻塞当前原生实现。**后果**：V3.0 多端需引入跨端框架或独立工程，但核心业务逻辑因 Repository 隔离可复用。

### ADR-2 运行时数据格式：JS 模块（轻量索引 + 按需分片）

| 候选 | 优势 | 劣势 | 状态 |
|------|------|------|------|
| JS 模块（require） | 100% 加载成功、体积小、可分包 | 需手写分片 | ✅ 采纳（运行层） |
| JSON | 标准、易读 | 基础库偶发加载失败、单文件 > 500KB 失败 | ❌ 弃用（运行时） |
| SQLite | 支持 SQL/索引 | 需插件、包体积大、只读 | ❌ 数据量小无需 |
| CSV | 体积极小 | 无嵌套、无类型 | ❌ 表达力不足 |
| Protocol Buffers | 体积极小、解析快 | 不可读、需编译 | ❌ 过度设计 |

**决策**：JS 格式 `require` 100% 成功；采用「轻量索引（56KB 启动）+ 按需分片（60KB/片）」：启动仅加载索引，搜索用索引，点击详情时按需加载分片。单文件 ≤ 152KB，扩展至 2000 条只需 40 个分片。**后果**：需维护分片脚本，但规避了 JSON 加载失败与单文件限制风险。

### ADR-3 维护层数据格式：Excel (.xlsx)

非技术人员可直接编辑、多 sheet 组织、支持筛选排序；编辑后经转换脚本生成 JS 分片。

### ADR-4 搜索方案：本地关键词提取 + 场景选项卡 + 索引名称匹配

| 候选 | 优势 | 劣势 | 状态 |
|------|------|------|------|
| 本地关键词提取 + 场景选项卡 + 索引匹配 | 零 API 成本、< 20ms、离线、透明可信 | 需维护 330+ 词库、NLP 能力有限 | ✅ 采纳（当前） |
| 本地倒排索引（JS） | 离线、全文检索 | 索引 696KB 超限 | ⚠️ 已弃用（代码保留） |
| 第三方库（flexsearch） | 功能强 | +50KB、学习成本 | ⚠️ V2.0 量大时考虑 |
| 后端搜索 API（Elasticsearch） | 复杂查询强 | 需服务器、不离线、成本高 | ❌ V3.0 再考虑 |
| AI 大模型语义理解 | NLP 强 | API 费用、依赖网络、不可解释 | ⚠️ V2.0 可选接入，架构预留 |

**决策**：当前纯本地方案零成本。用户输入自然语言 → 正向最大匹配从 330+ 词库提取核心关键词 → 匹配 2-5 个场景选项卡 → 轻量索引（56KB）做名称匹配 + 关键词权重。AI 完全可选，开发者自选厂商（豆包/通义千问/OpenAI 等）、协议、模型。

### ADR-5 状态管理：小程序原生（Page data + globalData）

| 候选 | 优势 | 劣势 | 状态 |
|------|------|------|------|
| 原生 globalData + 本地存储 | 无依赖、性能好 | 复杂状态需手动 | ✅ 采纳 |
| MobX | 响应式 | 增加依赖 | ❌ 当前复杂度低 |
| Redux | 可预测 | 模板代码多 | ❌ 过度设计 |

### ADR-6 后端服务（V2.0 预留）

| 候选 | 优势 | 劣势 | 状态 |
|------|------|------|------|
| 微信云开发 | 免运维、深度集成、按量付费 | 厂商锁定 | ✅ V2.0 采纳 |
| 自建后端（Node + MySQL） | 完全可控 | 需运维、周期长 | V3.0 迁移 |
| Serverless（阿里云/腾讯云函数） | 免运维、弹性 | 厂商锁定、冷启动 | 备选 |

### ADR-7 技术栈总览

| 层级 | 技术选型 | 用途 |
|------|----------|------|
| 前端框架 | 微信小程序原生 | UI/交互/路由 |
| 语言 | JavaScript (ES6+) | 业务逻辑 |

## 3. 系统架构设计

### 3.1 整体架构（分层）

```
┌─────────────────────────────────────────────────────────────────┐
│                        微信小程序（客户端）                         │
├─────────────────────────────────────────────────────────────────┤
│  表现层 (View/Pages): 首页│搜索│渠道详情│话术详情│分类│我的│工具箱  │
│        │ 依赖                                                 │
│  服务层 (Services): SearchService│ChannelService│ScriptService   │
│        │ FavoriteService│HistoryService│ConfigService            │
│        │ 【预留】AIService│ComplaintService│UserService          │
│        │ 依赖注入                                             │
│  数据访问层 (Repositories): ChannelRepository(接口)             │
│        ├─ LocalChannelRepository (当前, 本地JSON)              │
│        └─ 【预留】RemoteChannelRepository (V3.0, 远程API)      │
│        ScriptRepository│PlatformRepository│ConfigRepository      │
│        │                                                     │
│  数据层 (Data): channels_index.js(56KB,启动)│channels_part_N  │
│        详情分片(60KB,按需)│scripts.js│config.js│categories.js  │
│        本地存储: favorites / view_history / search_history      │
│  基础设施层 (Infra): SearchIndex│Tracker│Storage│SynonymDict│Validator │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  数据管线（离线工具链）                                            │
│  Word(.docx) → convert.py --mode extract → Excel(.xlsx)         │
│  → 人工审核 → convert.py --mode build → JS 分片 + Schema 校验     │
│  → 打包进小程序                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 分层原则

| 层级 | 职责 | 依赖方向 | 变更频率 |
|------|------|----------|----------|
| 表现层 | 渲染、交互、事件 | 依赖 Service | 高 |
| 服务层 | 业务编排、数据加工 | 依赖 Repository 接口 | 中 |
| 数据访问层 | 存取、查询、索引 | 依赖数据层 | 低 |
| 数据层 | 原始数据、本地存储 | 无依赖 | 中（内容更新） |
| 基础设施层 | 索引、埋点、存储、校验 | 无依赖 | 低 |

**依赖规则**：上层依赖下层接口，不依赖实现。Service 依赖 Repository 接口，不依赖 `LocalChannelRepository` 具体类（依赖倒置原则）。

### 3.3 模块划分与分包约束

| 模块 | 目录 | 职责 | 优先级 |
|------|------|------|--------|
| 首页 | pages/home/ | 首页渲染、搜索/分类入口、高频话术 | P0 |
| 搜索 | pages/search/ + services/SearchService.js | 联想、结果、高亮 | P0 |
| 渠道 | pages/channel-detail/ + services/ChannelService.js | 详情、分类、拨打、复制 | P0 |
| 话术 | pages/script-detail/ + services/ScriptService.js | 列表、详情、复制 | P0 |
| 个人中心 | pages/mine/ + services/FavoriteService.js | 收藏、历史 | P1 |
| 工具箱 | pages/toolbox/ | 跟进时间表、热线速查、企业查询 | P1 |
| 数据管线 | tools/ | Word→Excel→JS 转换、校验 | P0 |
| 基础设施 | utils/（detail/utils/） | 索引、埋点、存储、同义词、校验 | P0 |

> **分包约束（关键）**：
> 1. 主包（main）代码**不得** `require` 子包（subpackage）内模块；子包可 require 主包模块。
> 2. 仅被 detail 分包使用的工具函数（如 `source-utils.js`）须置于 `detail/utils/`，否则主包质量扫描报「未使用文件」。
> 3. 目录自动 index 解析不可靠：`require('./repositories')` 需显式落到 `repositories.js` 扁平入口。
> 4. 变更目录/新增文件后，开发者工具需「清除缓存 → 全部清除 → 重开项目」丢弃旧模块表缓存。

## 4. 核心模块设计

### 4.1 搜索时序（Sequence）

```
用户         SearchService      SearchIndex      SynonymDict      ChannelRepository

 │ 输入 query     │                 │                │                 │

 │                │ 正向最大匹配    │                │                 │
 │                │────────────────│                │                 │
 │                │  提取关键词     │                │                 │
 │                │◀───────────────│                │                 │
 │                │ 查同义词(469)   │                │                 │
 │                │────────────────────────────────▶│                 │
 │                │ 规范化词        │                │                 │
 │                │◀────────────────────────────────│                 │
 │                │ 索引名称匹配+权重│                │                 │
 │                │────────────────│                │                 │
 │                │ 候选渠道(id列表)│                │                 │
 │                │◀───────────────│                │                 │
 │   场景选项卡   │                 │                │                 │
 │◀───────────────│                 │                │                 │
 │ 点选场景/渠道  │                 │                │                 │

 │                │──────────────────────────────────────────────────▶│
 │                │ 按需加载 part_N │                │                 │

 │  渠道详情      │                 │                │                 │
 │◀───────────────│                 │                │                 │
```

### 4.2 搜索模块

- 关键词提取：正向最大匹配（330+ 词库）。
- 场景选项卡：2-5 个候选，用户点选。
- 联想：输入 ≥ 1 字防抖 300ms，前缀匹配 + 历史，最多 8 条。
- 高亮：标题/描述关键词黄色高亮。
- 降级：索引构建失败 → 字符串包含匹配。

### 4.3 渠道详情模块

- 基本信息卡（电话大号绿色、网址、监管部门）。
- 适用范围 / 前置条件 / 法律依据 / 实用提示（空则隐藏）。
- 关联话术卡（形成闭环）。信息来源（验证日期 + 来源）。

### 4.4 收藏与历史模块

- 本地存储 + 分组（重命名/排序/批量移动）。
- 搜索历史最多 20 条。

### 4.5 埋点（Tracker）

- 本地存储匿名日志（query + 时间），架构预留服务端上报。
- 事件：`home_view` / `search_submit` / `search_result_click` / `search_no_result` / `emergency_call_confirm` 等。

## 5. 数据模型设计

### 5.1 实体关系（ERD，文本化）

```
category 1──* channel *──1 platform(受理/监管)
channel 1──* script(关联话术)        script *──1 channel
channel 1──* 【预留】complaint_ticket
complaint_ticket 1──* 【预留】evidence
channel 1──* 【预留】channel_feedback
config(独立, 含 synonym_dict/hot_words/feature_flag)
```

### 5.2 核心表结构（字段级）

| 表 | 字段 | 类型 | 说明 |
|----|------|------|------|
| channel | id | string | 主键 |
| | name | string | 渠道名称 |
| | phone | string? | 投诉电话（空隐藏） |
| | url | string? | 网址（空隐藏） |
| | scope | string? | 适用范围 |
| | precondition | string? | 前置条件 |
| | legal_basis | string? | 法律依据 |
| | tags | string[] | 标签（≥3） |
| | category | string | 分类 id |
| | hot_level | int 1-5 | 热度权重 |
| | part_num | int | 分片号 |
| | path_type | enum | 路径类型：gov(政府部门)/legal(法律渠道)/regulator(监管部门)/media(媒体曝光) |
| | materials | json? | 所需材料清单（数组：名称 + 必填/建议 + 说明），渠道/话术详情展示 |
| | ext | json | 预留：effect_rating/response_speed/city_code |
| platform | id, name, url, positioning, target | — | 高层级平台 |
| script | id, scene, phone_version, written_version, placeholders, legal_basis, related_channel | — | 话术模板 |
| law | id, name, clause, content | — | 法规条款 |
| category | id, name, parent_id, order | — | 分类树 |
| config | data_version, synonym_dict, hot_words, feature_flag | — | 当前 data_version=2026.09.7 |

### 5.3 三层数据架构与分片

```
Word（源）→ Excel（维护层）→ JS 分片（运行层）→ 小程序
```

- 启动：Word → extract → Excel（审核）→ build → JS 分片。
- 日常改 Excel：build → JS 分片（自动重新分片）。
- 分片规则：每分片 50 条渠道（约 60KB）；索引仅含 id/name/phone/tags/part_num/category（56KB）；渠道增长自动新增分片，无需改代码。

### 5.4 Repository 模式（数据访问抽象）

```javascript
// 数据访问层抽象，Service 仅依赖接口
const { channels: channelRepo } = require('../repositories').createRepositories();
// 当前：LocalChannelRepository；V3.0：RemoteChannelRepository（Service/View 零改动）
```

### 5.5 加载策略（utils/data.js）

1. 启动加载 `channels_index.js`（56KB）+ `config.js` + `categories.js` + `scripts.js`。
2. 搜索只查索引（名称匹配 + 关键词权重），不加载详情。
3. 点击详情按 `part_num` 按需加载对应 `channels_part_N.js`。
4. 已加载分片缓存内存（Map），重复访问 < 10ms。
5. `getChannelById()` 自动判断分片，上层无感知。

## 6. 性能设计（SLA）

| 指标 | SLA 目标 | 当前实测 |
|------|----------|----------|
| 冷启动 | < 2s | 启动解析 ~171KB（量级达标，建议真机实测） |
| 搜索响应 | < 500ms（p95 < 2s） | Node 基准 avg 0.42ms / p95 1.43ms / max 4.08ms（424 样本） |
| 主包体积 | < 1MB | 索引 56KB + 资源，余量充足 |
| 单文件 | ≤ 500KB | 最大 152KB |
| 内存 | 可控 | 仅加载已浏览分片 |

**规模演进（容量规划）**：

| 渠道数 | 索引 | 分片数 | 启动加载 | 单文件最大 |
|--------|------|--------|----------|------------|
| 122（当前） | 56KB | 3 | 56KB | 60KB |

## 7. 安全与合规设计（威胁建模）

### 7.1 威胁模型（STRIDE 简化）

| 威胁 | 场景 | 缓解 |
|------|------|------|
| 信息泄露（Spoofing/Tampering） | 本地存储被读取 | 仅存非 PII；前缀隔离 `wqt_` |
| 合规越界（Repudiation） | 用户误以为平台代投诉 | 备案备注 + 页面显著声明 |
| 内容失真（Tampering） | 渠道信息过时 | 验证日期 + 来源标注 + 版本更新 |
| 拒绝服务（DoS） | 超大索引拖慢启动 | 分片 + 懒加载 + 降级匹配 |

### 7.2 合规设计矩阵

| 项 | 设计 |
|----|------|
| 个人信息保护 | 遵循《个人信息保护法》；当前不收集任何个人信息（无用户 ID、手机号、位置、openid） |
| 隐私政策 | 当前无个人信息收集，无需隐私政策；V2.0 接入登录时补充 |
| 内容审核 | 内容均来自政府公开渠道，无 UGC，无违法违规内容 |
| 紧急入口 | 二次确认防误触 |
| 备案合规 | 信息工具定位，不代理/不代投诉；备案备注明确免责与虚假投诉责任 |
| 数据安全 | 本地存储前缀隔离（wqt_），clearAll 仅清前缀 key |

## 9. 扩展性演进路线

### 9.1 当前 → V2.0（云开发 + AI）

```
本地 JSON      ──保持──▶   本地 JSON（基础数据）
本地索引      ──保持──▶   本地索引（基础搜索）
本地存储      ──扩展──▶   本地 + 云数据库
无后端        ──新增──▶   微信云开发
无 AI         ──新增──▶   大模型 API（豆包/通义千问）
无用户        ──新增──▶   微信登录（openid）
```

各模块通过新增实现类/页面升级，Service/View 零改动（接口隔离）。

### 9.2 V3.0（独立后端 + 开放 API）

```
微信云开发    ──迁移──▶   独立后端（Node + MySQL + Elasticsearch）
云数据库      ──迁移──▶   MySQL + Redis
云函数        ──迁移──▶   微服务（Docker + K8s）
大模型直连    ──优化──▶   后端代理（统一鉴权/限流/缓存）
无 API       ──新增──▶   RESTful API + API Key
无 CMS       ──新增──▶   内容管理后台
```

Repository 切换示例（Service/View 零改动）：

```javascript
// app.js（V3.0）
const RemoteChannelRepository = require('./repositories/RemoteChannelRepository');
App({ globalData: { repositories: { channel: new RemoteChannelRepository('https://api.wobeiqifu.com/v1', API_KEY) } } });
```

### 9.3 数据迁移（V2.0）

1. 用户首次登录检测本地收藏/历史。
2. 云函数 `migrateUserData` 上传至云数据库。
3. 本地保留作缓存，云端为权威源（冲突云端优先）。
