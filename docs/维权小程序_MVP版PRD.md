## 1. 项目背景

### 1.1 业务背景

现有三份维权资料（《官方投诉维权渠道大全》《生活投诉渠道大全》《群众诉求官方平台汇总》）合计超11万字、260+表格，覆盖51个生活领域、109个行业投诉渠道、16个高层级诉求平台。信息密度极高但存在以下问题：

| 问题 | 具体表现 | 用户损失 |
|------|----------|----------|
| 检索困难 | 长文档无结构化检索，需逐页翻找 | 遇到问题时无法快速定位对口渠道 |
| 信息分散 | 电话、网址、话术、流程分散在不同章节 | 需在多个位置拼凑完整维权方案 |
| 时效风险 | 热线频繁整合（12369→12345、12358→12315等12条已变更） | 拨打失效号码，延误维权时机 |
| 专业门槛 | 话术需引用法律条文，普通用户不会写 | 投诉因表述不规范被不予受理或调解无果 |
| 流程缺失 | 投诉后不知道多久该有结果、超期该怎么办 | 投诉石沉大海后不知如何升级 |

### 1.2 产品机会

维权是全民高频刚需场景（全国12315年受理超3000万件、12345年受理超1亿件），但市场上缺乏一款覆盖"找渠道→写话术→跟流程"全链路的工具型产品。现有竞品均为单部门视角或纯电话簿，存在明确的产品空白。

### 1.3 文档目的

本文档定义维权通 V1.0（MVP）的完整产品需求，作为设计、开发、测试的唯一依据。同时在数据模型、技术架构、功能布局上为 V2.0（AI智能问答+投诉进度管理）、V2.5（社区+多城市）、V3.0（平台化）预留扩展接口，避免未来重构。

## 2. 产品目标与范围

### 2.1 产品定位

**一句话定位**：输入关键词，秒出投诉电话、网址、话术和流程的随身维权工具箱。

**核心价值主张**：
- **找得到**：109+官方渠道结构化入库，关键词搜索直达
- **用得上**：5套高频场景话术（电话版+书面版），一键复制即用
- **走得对**：每个渠道标注监管部门、受理范围、前置条件，避免找错门
- **跟得住**：投诉跟进时间表提醒每个节点的行动和升级路径

### 2.2 MVP 目标

| 维度 | 目标值 | 度量方式 |
|------|--------|----------|
| 内容覆盖 | 109个行业渠道 + 16个高层级平台 + 5套话术 + 1套通用模板 100%收录 | 数据录入核对清单 |
| 搜索体验 | 搜索响应 < 500ms，首条命中率 ≥ 80% | 内部测试用例（50个典型query） |
| 核心路径 | 搜索→查看渠道→复制话术 ≤ 3次点击 | 交互走查 |
| 技术指标 | 冷启动 < 2s，主包体积 < 1MB | 性能测试 |
| 上线目标 | 微信小程序审核一次通过 | 审核结果 |

### 2.3 范围定义

#### 2.3.1 In Scope（MVP 做）

| 模块 | 功能点 | 优先级 |
|------|--------|--------|
| 搜索 | 关键词全文检索、搜索联想、热门搜索词、搜索历史 | P0 |
| 渠道详情 | 渠道信息展示、电话拨打、网址复制、收藏 | P0 |
| 分类浏览 | 四大类+二级分类树浏览、渠道卡片列表 | P0 |
| 话术模板 | 5个场景话术（电话版+书面版）、一键复制、占位符引导 | P0 |
| 通用投诉信 | 结构化通用模板、一键复制 | P1 |
| 收藏 | 收藏渠道/话术、本地存储、收藏列表 | P1 |
| 工具箱 | 跟进时间表、热线变更速查、企业查询指引、关于页 | P1 |
| 紧急入口 | 110/119/120/96110 一键拨打（二次确认） | P0 |

#### 2.3.2 Out of Scope（MVP 不做，预留接口）

| 功能 | 计划版本 | MVP 预留方式 |
|------|----------|--------------|
| 用户注册登录 | V2.0 | user表结构定义；所有用户行为用 device_id 临时标识，可未来绑定 user_id |
| AI 智能问答 | V2.0 | ai_conversation 表结构定义；数据访问层预留 AIService 接口；首页预留AI入口位置（隐藏） |
| 投诉进度管理 | V2.0 | complaint_ticket 表结构定义；工具箱页预留"我的投诉"入口（隐藏） |
| 证据管理 | V2.0 | evidence 表结构定义；话术详情页预留"添加证据"入口（隐藏） |
| 话术定制生成 | V2.0 | script 表预留 script_type（template/ai_generated/custom）字段 |
| 效力评级可视化 | V2.0 | channel 表预留 effect_rating、response_speed、penalty_power 等字段 |
| 维权案例社区 | V2.5 | post、comment、like 表结构定义；底部导航预留第5个tab位置 |
| 多城市支持 | V2.5 | channel 表预留 city_code 字段；MVP 默认 national/sichuan/chengdu |
| 用户反馈渠道效力 | V2.5 | channel_feedback 表结构定义 |
| 开放 API | V3.0 | 数据访问层按 Repository 模式抽象，可无缝替换为远程实现 |
| 内容管理后台 | V2.0 | 数据与代码完全分离，JSON Schema 定义清晰，未来可直接接入CMS |
| 支付/增值服务 | V2.5 | order、payment 表结构定义；不启用 |
| 消息推送 | V2.0 | 预留订阅消息模板ID配置位；投诉跟进提醒逻辑预留 |

### 2.4 与远景规划的衔接原则

1. **数据模型先行**：所有 V2.0/V2.5/V3.0 涉及的核心数据表，在 MVP 阶段即完成结构定义并写入数据字典，开发时建表但不启用业务逻辑
2. **扩展字段兜底**：每张核心业务表预留 `ext`（JSON 类型）字段，用于未来新增属性无需改表结构
3. **接口抽象**：数据访问层按 Repository + Service 两层抽象，MVP 用本地实现，未来迁移后端时仅替换实现类
4. **配置化运营**：搜索权重、热门搜索词、分类配置、功能开关均放入配置层，运营可动态调整，无需发版
5. **页面占位**：未来功能的入口位置在页面布局中预留（默认隐藏），V2.0 上线时仅需取消隐藏+联调，无需改版

## 3. 用户与场景

### 3.1 目标用户画像

| 用户类型 | 人口特征 | 核心诉求 | 技术熟练度 | 使用频率 |
|----------|----------|----------|------------|----------|
| 普通消费者 | 20-45岁，有网购/线下消费经历 | 快速找到对口投诉渠道和话术 | 中 | 低频（遇到问题时） |
| 职场劳动者 | 22-50岁，在职/离职 | 欠薪、社保、公积金、劳动仲裁路径 | 中 | 低频 |
| 业主/租户 | 25-50岁，有房产或租房 | 物业不作为、乱收费、房屋质量 | 中低 | 中频 |
| 金融消费者 | 25-55岁，有银行/保险/证券业务 | 销售误导、乱收费、理赔纠纷 | 中 | 低频 |
| 政务诉求者 | 30-60岁，与政府部门打过交道 | 基层不作为、需要上级督办 | 中低 | 低频 |
| 中老年用户 | 50岁+，智能手机基础操作 | 大字、大按钮、步骤清晰 | 低 | 低频 |

### 3.2 核心使用场景

#### 场景 A：快递丢失，商家与快递公司互相推诿

**触发**：用户快递丢失，向快递公司客服投诉7天未解决。

**路径**：
1. 打开小程序 → 首页搜索框输入"快递丢了"
2. 搜索联想下拉显示"快递丢失/破损/延误"→ 点击
3. 搜索结果首条：国家邮政局申诉平台（12305），卡片标注"需先向企业投诉满7日"
4. 点击进入渠道详情页 → 查看适用范围、前置条件、法律依据
5. 底部"关联话术"模块 → 点击"查看完整话术"
6. 话术详情页 → 点击"复制电话版"→ 拨打12305照着念

**成功标准**：从打开小程序到拿到话术 ≤ 30秒，≤ 3次点击。

#### 场景 B：物业公司乱收费，多次反映无果

**触发**：用户小区物业擅自提高物业费，多次向物业反映无果。

**路径**：
1. 首页 → 点击"社会服务与政务司法"分类 → 展开"房地产/物业"
2. 渠道列表展示：12345（住建承办）+ 成都本地渠道（028-12345）
3. 点击12345渠道详情 → 查看投诉流程（先物业→12345→住建→升级信访）
4. 关联话术自动匹配"物业"场景 → 话术含《物业管理条例》第四十一条+《民法典》第九百四十二条
5. 点击收藏 → 后续书面投诉时从收藏页调用

#### 场景 C：不确定该找哪个部门，按领域浏览

**触发**：用户遇到问题但不确定属于哪个领域。

**路径**：
1. 首页 → 四大分类入口 → 点击"金融与商业消费"
2. 分类页左侧一级分类，右侧展开二级分类：银行、保险、证券、消费者权益、电商、价格监管...
3. 点击"银行"→ 渠道卡片列表：12378金融监管、12363人行、互联网金融举报平台
4. 每张卡片显示电话+一句话适用范围 → 点击进入详情

#### 场景 D：紧急情况

**触发**：用户遭遇正在发生的诈骗或人身安全威胁。

**路径**：
1. 打开小程序 → 首页红色紧急电话条 → 点击"110报警"
2. 二次确认弹窗："确认拨打110报警电话？"→ 确认
3. 调起系统拨号界面

## 5. 功能需求详述

### 5.1 首页

#### 5.1.1 功能描述

首页是小程序的主入口，承载搜索、紧急入口、分类导航、高频话术、最近浏览五大核心模块。

#### 5.1.2 页面结构（从上到下）

| 区域 | 占比 | 内容 | 优先级 |
|------|------|------|--------|
| 顶部搜索区 | ~20% | 搜索框 + 热门搜索词标签 | P0 |
| 紧急电话条 | ~8% | 110/119/120/96110 四个圆形按钮 + 提示文案 | P0 |

| 优先级 | 匹配类型 | 示例 |

### 6.5 数据来源与处理规范

#### 6.5.1 数据来源

| 数据类型 | 来源文档 | 提取方式 |
|----------|----------|----------|
| 行业投诉渠道 | 《官方投诉维权渠道大全》第二编 + 《生活投诉渠道大全》 | 从表格中提取，去重合并 |
| 高层级诉求平台 | 《群众诉求官方平台汇总》+ 《官方投诉维权渠道大全》第三编 | 从结构化文本中提取 |
| 话术模板 | 两份文档的"实战工具与模板"编 | 5个场景+通用模板 |
| 跟进时间表 | 两份文档的"投诉跟进与升级时间表" | 表格提取 |
| 热线整合 | 两份文档的"热线整合变更速览" | 表格提取 |
| 企业查询 | 两份文档的"投诉前先查底细" | 表格提取 |

#### 6.5.2 数据处理标准

1. **去重**：三份文档中重复出现的渠道（如12315在多个分类出现）合并为一条，关联多个分类标签
2. **字段补全**：每个渠道必须补全 `tags`（≥3个）、`category_l1`、`category_l2`、`hot_level`、`status`、`city_code`
3. **状态标注**：已整合/停用的热线标注 `status=merged/discontinued`，并填写 `merged_to`
4. **标签规范**：标签覆盖官方术语+用户口语化表达，如官方"违规收费"+口语"乱扣费""多收钱"
5. **验证日期**：所有数据标注 `data_verified_at=2026-08-30`
6. **JSON格式**：最终数据输出为标准JSON，UTF-8编码，通过JSON Schema校验

#### 6.5.3 数据质量验收标准

- 渠道收录完整率：100%（对照三份文档清单逐条核对）
- 字段完整率：核心字段（name/phone/scope/category/tags）100%非空
- 电话号码格式准确率：≥98%（人工抽检20条）
- 网址可访问率：≥95%（抽检）
- 标签覆盖率：每个渠道≥3个标签
- JSON Schema校验通过率：100%

### 7.3 扩展性架构设计

#### 7.3.1 Repository 模式（核心扩展点）

数据访问层按 Repository 接口模式设计，MVP使用本地实现，未来迁移后端时仅替换实现类，上层代码零改动：

```javascript
// 接口定义
class ChannelRepository {
  getById(id) {}
  search(keyword, filters) {}
  getByCategory(categoryL1, categoryL2) {}
  getHot(limit) {}
}

// MVP实现：本地JSON
class LocalChannelRepository extends ChannelRepository {
  constructor() {
    this.data = require('/data/channels.json');
    this.index = this.buildIndex();
  }
  // ... 实现方法
}

// V3.0实现：远程API
class RemoteChannelRepository extends ChannelRepository {
  constructor(apiBaseUrl) {
    this.apiBaseUrl = apiBaseUrl;
  }
  // ... 调用后端API实现
}

// Service层依赖接口，不依赖具体实现
class ChannelService {
  constructor(repository) {
    this.repository = repository; // 注入，可切换本地/远程
  }
}
```

### 7.5 安全与合规

- 所有内容强调"依法维权、理性维权"

#### 7.5.3 小程序审核合规

- 不涉及医疗、金融、法律等需要特殊资质的类目（定位为"工具/信息查询"）
- 不提供在线法律服务（话术模板为通用信息，非法律意见）
- 不涉及UGC内容（MVP无社区，V2.5上线时需先审后发）
- 紧急电话拨打功能符合微信小程序规范

## 11. 搜索策略升级（应对用户千奇百怪的描述）

### 11.1 问题定义

用户不会按照预设关键词搜索。实际用户输入可能包括：

| 输入类型 | 示例 | 当前方案能否处理 |
|----------|------|-----------------|
| 标准关键词 | "快递丢失"、"12305" | ✅ 能处理 |
| 口语化表达 | "快递被偷了"、"话费莫名其妙被扣了" | ⚠️ 部分处理（靠同义词） |
| 自然语言描述 | "我在淘宝买了个假货商家不给退钱怎么办" | ❌ 处理不了 |
| 情绪宣泄 | "被坑死了"、"气死我了没人管" | ❌ 处理不了 |
| 错别字/拼音 | "kuaididiu"、"快地丢了" | ❌ 处理不了 |
| 场景描述 | "物业公司把我电梯停了一个星期" | ❌ 处理不了 |
| 多问题组合 | "快递丢了而且商家还不给退款" | ❌ 处理不了 |

**核心矛盾**：用户有1000种表达方式，但渠道只有122个。必须建立从"用户任意表达"到"标准渠道/话术"的映射桥梁。

### 11.2 四层搜索架构

```
┌─────────────────────────────────────────────────────────┐
│  第四层：AI语义理解（V2.0）                               │
│  大模型解析用户自然语言 → 提取{领域,问题类型,诉求}        │
│  → 匹配渠道+话术+步骤 → 多轮对话澄清                     │
├─────────────────────────────────────────────────────────┤
│  第三层：向量语义检索（V1.5/V2.0）                        │
│  渠道/话术向量化 → 用户问题向量化 → 语义相似度匹配        │
│  处理同义词、近义词、口语化表达                            │
├─────────────────────────────────────────────────────────┤
│  第二层：模糊匹配+拼音（V1.5）                            │
│  编辑距离匹配、拼音匹配、错别字纠正                        │
│  处理"kuaididiu"、"快地丢了"                             │
├─────────────────────────────────────────────────────────┤
│  第一层：关键词+标签+同义词（MVP，当前）                  │
│  倒排索引、标签加权、同义词典扩展                          │
│  处理标准关键词和常见口语                                  │
└─────────────────────────────────────────────────────────┘
```

**搜索执行流程**：用户输入 → 第一层匹配 → 结果足够好则返回 → 结果不足则触发第二层 → 仍不足则触发第三层 → V2.0触发第四层AI理解。

### 11.3 MVP核心：本地关键词提取+场景选项卡（零AI成本）

#### 11.3.1 设计理念

**核心问题**：用户不会按照预设关键词搜索。用户可能输入"我快递被偷了快递公司只赔我运费三倍我物品价值500块怎么办"——这一大段话里，核心关键词就是"快递""丢失""赔偿"。

**解决方案**：纯本地关键词提取+场景选项卡，完全不用AI，零API成本：

```
用户输入一大段自然语言
    ↓
本地关键词词库匹配（正向最大匹配，500+关键词）
    ↓
提取核心关键词：快递、丢失、赔偿
    ↓
场景匹配：关键词组合 → 匹配到2-5个相关场景
    ↓
展示场景选项卡（用户点选）
    ↓
进入对应渠道/话术详情
```

**优势**：
- **零成本**：纯本地计算，无API费用
- **响应快**：<20ms，比AI快100倍
- **可靠**：不依赖网络，不依赖第三方服务
- **可解释**：用户能看到匹配到的关键词和场景，透明可信
- **可扩展**：词库持续扩充，无需改代码

#### 11.3.3 关键词提取算法

**正向最大匹配算法**（从长到短匹配，避免"快递"被"快"单独匹配）：

```
输入："我快递被偷了快递公司只赔我运费三倍"
    ↓
1. 从位置0开始，最长匹配6个字
   "我快递被偷了" → 不在词库
   "我快递被偷" → 不在词库
   ...
   "我" → 不在词库，跳过
    ↓
2. 位置1，"快递被偷了快" → 不在词库
   "快递被偷了" → 不在词库
   "快递被偷" → 不在词库
   "快递" → 在词库！匹配成功，记录"快递"
    ↓
3. 位置3，"被偷了快递公司" → 不在词库
   ...
   "被偷" → 在词库（问题词）！匹配成功，记录"被偷"
    ↓
4. 继续匹配...
    ↓
提取结果：["快递", "被偷", "快递公司", "赔偿"]
```

**匹配优先级**：
1. 场景映射精确匹配（关键词组合全部命中）→ 优先级最高
2. 领域词+问题词组合匹配 → 优先级高
3. 单个领域词匹配 → 优先级中
4. 单个问题词匹配 → 优先级低
5. 无匹配 → 展示热门场景+全部分类

### 11.6 V2.0阶段：AI语义理解+RAG向量检索

#### 11.5.1 RAG向量检索

- 将所有渠道/话术文本向量化（使用text-embedding模型）
- 用户问题向量化后，计算语义相似度，返回最相关的渠道/话术
- 优势：能处理"我在淘宝买了个假货商家不给退"这种自然语言
- 实现：向量索引预构建（转换脚本生成），小程序端加载向量索引做相似度计算，或V2.0走云函数

#### 11.5.2 AI语义理解

### 11.7 V3.0阶段：智能路由+个性化推荐

- **智能路由**：根据用户问题，自动推荐最佳投诉渠道组合（先A后B再C），而不是单个渠道
- **个性化推荐**：基于用户历史搜索、收藏、投诉跟踪记录，推荐相关渠道
- **上下文感知**：根据时间（如315期间推荐12315）、地点（如成都用户推荐成都12345）、用户画像调整推荐
- **成功率预测**：基于用户反馈数据，预测每个渠道的成功率，优先推荐高成功率渠道

#### 12.2.2 各端技术方案详解

**微信小程序（V1.0）**：
- UI层：WXML/WXSS原生
- 核心层：JS模块（与其他端共享）
- 优势：微信生态流量大、无需安装、分享方便
- 限制：包体积2MB（主包）、不能直接拨打电话（需用户确认）、审核严格

**H5/PC网站（V1.5/V2.0）**：
- UI层：HTML/CSS/JS，响应式布局（移动端优先，PC端大屏适配）
- 核心层：同一套JS模块
- 部署：静态网站，可部署在GitHub Pages、Vercel、阿里云OSS等
- 优势：无需安装、跨平台、SEO可收录、更新无需审核
- PC端额外功能：大屏数据看板、批量查询、打印投诉信

**APP（V2.0）**：
- 技术方案：Capacitor（Ionic团队出品）将Web代码打包为原生APP
- UI层：同一套Web响应式UI
- 原生能力：通过Capacitor插件调用原生API（电话、通知、相机、文件系统）
- 优势：可上架App Store/应用商店、推送通知、离线体验更好、可访问更多原生能力
- 构建：一条命令同时生成iOS和Android安装包

**Windows EXE（V2.5）**：
- 技术方案：Tauri（Rust+WebView2，比Electron轻10倍）
- UI层：同一套Web响应式UI
- 安装包体积：约5-10MB（Electron通常80MB+）
- 优势：桌面端体验、系统托盘、开机自启、本地文件操作、完全离线
- 适用场景：律师/法务工作者桌面工具、批量处理投诉材料

**macOS/Linux（V3.0）**：
- Tauri天然跨平台，同一套代码编译为macOS/.dmg和Linux/.AppImage

#### 12.2.3 核心层跨端复用机制

**搜索索引模块**（纯JS，无平台依赖）：
- 倒排索引构建、搜索、排序、分词
- 所有端使用同一份代码，确保搜索结果一致
- 预构建索引文件（search_index.json）所有端共享

**数据管理模块**（Repository模式）：
- 定义统一接口：getById、search、getByCategory、getHot
- 各端实现不同存储：
  - 小程序：wx.setStorageSync + 本地JSON
  - Web：localStorage + IndexedDB
  - APP：Capacitor Storage + 本地文件
  - EXE：Tauri FS + SQLite（可选）
- Service层代码完全不变，只替换Repository实现

**业务逻辑模块**（Service层）：
- SearchService、ChannelService、ScriptService、FavoriteService
- 纯业务逻辑，无平台API调用
- 所有端100%复用

**埋点模块**：
- 统一track(event, params)接口
- 各端实现不同上报通道
- V2.0后统一上报到后端

### 12.4 多端数据同步策略（V2.0）

- **权威数据源**：云数据库（V2.0接入微信云开发）
- **各端缓存**：本地缓存热门数据+最近浏览数据
- **同步策略**：
  - 启动时检查数据版本，有更新则增量同步
  - 收藏/历史/投诉跟踪数据实时双向同步
  - 离线时操作本地缓存，联网后自动同步（冲突处理：云端优先+人工确认）
- **数据格式**：所有端使用统一JSON Schema，确保数据可互导

### 12.5 发布优先级与资源需求
