### 9.1 搜索命中率回归测试执行结果（R2）
- 脚本：`scripts/search-hitrate-test.js`（复刻 `search-result.doSearch` 合并逻辑，离线跑 53 个口语化 query）。
- **首条命中率 (rank1)：51/53 = 96.2%**（目标 ≥80% → ✅ 达标）。
- **召回率@5：53/53 = 100.0%**。
- 2 条未首条命中（均为「召回@5 命中、仅排序靠后」，属优化项而非缺陷）：
  - `信用卡乱收费`：期望 12378，`top1` 为通用 12345，但 12378 在 top5（rank3）。
  - `快递柜乱收费`：期望 12305，`top1` 为通用 12345，但 12305 在 top5（rank3）。
  - 原因：通用 12345 标签覆盖极广，排序分高于专项热线；可在搜索加权中提升「专项热线 vs 通用热线」区分度进一步优化（非阻塞）。

### 9.2 渠道标签覆盖全量统计（R7）
- 统计口径：全量读取 `data/channels_index.js`（122 条渠道）。
- **标签总数 2008，平均 16.46 标签/渠道，最多 25，最少 ≥3**。
- **标签 <3 的渠道：0 条（0.0%）；标签 =0 的渠道：0 条**。
- 结论：远超 PRD §6.5「每渠道 ≥3 标签」要求，无需补标签。

### 9.3 数据计数澄清（R4）
- 复核 PRD §6.1 数据模型：**channel 表目标「109+条」、platform 表目标「16条」** 是两张独立表，并非相加为 125。
- 实测：`channels_index.js` 共 **122 条渠道（≥109 ✅）**，`data-detail.js` 共 **18 个平台（≥16 ✅，且超额）**。
- **结论：渠道/平台数量均已满足 PRD，此前「差 3 条」为误将两张表目标相加所致，实为误报，无数据缺口。**
- 补充说明（非缺陷，仅信息项）：按 `categories.js` 二级分类核对，14 个二级类目下无「专属」渠道条目，这是因为相关行业由 12315 / 12345 / 12321 等综合热线兜底覆盖（如 价格监管/广告违法/知识产权/旅游/文化广电 等均已并入 12315 或 12345）。如需更精细，可将这部分行业在分类页增加「指向综合热线的引导」，非功能性阻塞。

### 9.4 搜索延迟基准（R6）
- 方法：Node 进程内对 53 个典型 query 复刻 `search-result` 合并逻辑，8 轮预热取 424 个样本计时（纯 JS 检索，不含 WXML 渲染；真机仅作量级参考）。
- 结果：**avg 0.42ms / p50 0.16ms / p95 1.43ms / max 4.08ms**，远低于 PRD §7.4 搜索响应 < 500ms 目标。
- 冷启动：受限于无微信运行环境无法直接测得，架构代理指标为「启动仅解析 ~171KB」；本地全量数据 + 分包懒加载，量级上满足 < 2s 目标，**建议上线前在真机/开发者工具性能面板补一次实测记录**（非代码缺陷）。
